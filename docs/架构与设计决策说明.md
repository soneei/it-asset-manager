# 架构与设计决策说明

> 本文解释 `it-asset-manager` 这套开源资产管理系统**为什么这样设计**。
> 面向：想看懂代码的人、想复用方法的人、以及把它当作作品集展示的人。
> 所有说明均为通用设计原理，不含任何真实企业 / 人员 / 资产数据。

---

## 1. 为什么用单文件 SQLite

| 维度 | 选择 SQLite 的理由 |
|---|---|
| 部署成本 | 零服务依赖，一个 `.db` 文件即数据库，拷贝即用 |
| 审计友好 | 单文件便于整体备份、整体哈希校验、整体快照（VACUUM INTO） |
| 中小规模够用 | 千级资产规模下，SQLite 性能完全胜任 |
| 可移植 | 可随项目目录带走，不绑云 |

**代价与对策**：SQLite 不适合高并发写。对策：所有写操作经统一入口（`asset_manager.py` 的 `assign` / `register` 等方法），避免多处直连导致锁竞争。

---

## 2. 为什么保留审计日志（operation_log）

这是整套系统的**灵魂决策**。

- `assets` 只存"当前状态"（最新快照），用于日常查询；
- `operation_log` 存"全部历史"（只追加事件），用于审计与回溯；
- 二者分离 = **查询效率**与**可追溯性**兼得。

写入原则：
- 事件不可变（append-only），绝不直接 UPDATE 历史；
- 每条事件带 `operator` / `timestamp` / `from_state` / `to_state`；
- 即使快照被误改，也能从事件流重算任意历史时点状态。

> 设计取舍：宁可多写一条日志，也不省一次留痕。审计价值 >> 存储节约。

---

## 3. 为什么标签只放稳定字段

物理标签是**长期附着在设备上的身份证**，而人员 / 部门 / 价格会频繁变动。

- 若把"使用人"印在标签上，一次调岗就要重打全部标签 → 成本与混乱；
- 正确做法：标签只印**品牌 / 编码 / 名称 / 配置·SN / 二维码**；
- 易变信息由扫码实时查库返回，标签与数据库通过"编码"解耦。

这一条直接决定了标签的**物理唯一性**和**低维护成本**。

---

## 4. 为什么双存储（SQLite + JSON）

- `assets.db`：结构化查询、事件流、审计的主存储；
- `assets.json`：轻量同步备份 / 跨工具消费（如前端静态页、外部报表）；
- 二者由同一写入入口保证一致，JSON 作为**可读副本**而非真相源。

> 真相源唯一（Single Source of Truth）：db 是真值，json 是派生。避免"两个库谁为准"的分裂。

---

## 5. 为什么扫码实时查库，而不是静态页

- 静态页（把详情烘进 HTML）一旦设备变更就过期，且需重生成全量；
- 实时查库：二维码只编码 `{BASE_URL}/{编码}`，服务端按编码实时返回最新状态；
- 好处：标签永不重打（除非稳定字段错），数据永远新鲜。

**部署注意**：`BASE_URL` 必须是**固定可达地址**（内网服务器或已备案域名）。地址多变的环境无法满足"固定地址"要求，应避免。

---

## 6. 代码组织（模块职责）

| 模块 | 职责 |
|---|---|
| `asset_manager.py` | 核心引擎：资产模型、状态机、事件写入、查询 |
| `asset_cli.py` | 命令行入口，封装常用操作 |
| `web_server.py` | 提供查询 API 与看板（含 `/api/scan/{code}` 扫码接口） |
| `gen_labels.py` | 批量生成标签（从 db 全量导出） |
| `gen_asset_detail.py` | 生成扫码详情页（本机 / 内网用） |
| `schema/schema.sql` | 表结构定义，单一数据源 |
| `sample_data/导入模板.xlsx` | 批量导入模板 |

设计约束：
- 所有写操作经核心引擎，禁止散落直连；
- 真实数据文件（`.db` / `.xlsx` / 照片）已被 `.gitignore` 屏蔽，仓库只含代码与结构。

---

## 7. 一句话总结这套设计

> **用最小的工程成本，把"便于审计"这件事做死做牢：单文件存储 + 事件溯源 + 标签解耦 + 真相源唯一。**
> 它不炫技，但每一处取舍都指向同一个目标——**出事的时候，能还原真相**。
