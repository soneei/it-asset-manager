# IT 资产全生命周期管理方法（通用版）

> 适用对象：中小企业 / 成长型团队的行政、IT 或内控岗位。
> 定位：一套**可审计、可落地、不依赖商业软件**的 IT 资产治理方法。
> 设计底座：COBIT（IT 治理）、ITIL v4（服务价值体系）、ISO/IEC 19770-1（IT 资产管理系统）、ISO/IEC 38500（IT 治理原则）。
> 本文件使用**虚拟公司「示例科技（EX）」与虚拟数据**，不含任何真实企业、人员或资产信息。

---

## 0. 一句话原则

> **资产系统的第一目标不是"记账"，而是"便于审计"。**
> 任何一次入库、领用、变更、退库、盘点，都必须留下**谁、在什么时点、对哪台资产、做了什么**的不可篡改痕迹。
> 这一条决定了后面所有的设计取舍。

---

## 1. 资产分类与编码体系设计

### 1.1 分类维度（按物理形态 + 价值密度）

| 类别码 | 含义 | 典型设备 |
|---|---|---|
| `LAP` | 笔记本电脑 | 员工日常办公笔记本 |
| `DES` | 台式机 / 主机 | 开发机、设计工作站 |
| `MON` | 显示器 | 外接屏 |
| `NET` | 网络设备 | 路由器、交换机、扩展坞 |
| `MOB` | 移动终端 | 手机、平板 |
| `PRN` | 打印 / 外设 | 打印机、扫描仪 |
| `SRV` | 服务器 | 本地小型服务器 |
| `OTH` | 其他 | 线缆、配件等 |

### 1.2 编码规则（物理唯一身份）

```
格式： {ORG}-{CATEGORY}-{YYYY}-{SEQ}
示例： EX-LAP-2026-0001
              │    │       │      └ 四位流水号（同年度内唯一）
              │    │       └──────── 入库年份
              │    └──────────────── 类别码（见 1.1）
              └───────────────────── 组织前缀（虚拟化示例，取 Example 首字母）
```

**铁律（物理唯一性）**：
- 每一个资产编码 = 一台设备的**唯一物理身份**。
- 编码一旦生成并贴标，**稳定字段永不可改**（见第 3 节）。改任何一个稳定字段 = 已贴标签全部失效，必须重打。
- 新入库设备按规则顺延流水号；**已生成的编码和二维码绝对不再修改**。

### 1.3 稳定字段 vs 易变字段

| 字段类型 | 字段 | 是否入标签 | 理由 |
|---|---|---|---|
| 稳定 | 品牌、资产编码、名称、配置·SN、二维码 | ✅ 入 | 设备生命周期内不变 |
| 易变 | 使用人、部门、工位、采购价、采购日期 | ❌ 不入 | 会随人员流动/调拨变化，写进标签就废了 |

> 经验：标签只承载"这台设备是什么"，不承载"谁在用"。使用人等易变信息由系统实时查库返回，而不是刻死在物理标签上。

## 2. 二维码标签的物理唯一性规则

### 2.1 为什么用二维码

- 扫码即可在手机上实时拉取该资产的当前状态（在用 / 闲置 / 维修中 / 已处置）、使用人、配置、流转历史。
- 比纸质台账更快核对，盘点时"扫一个、对一条"。

### 2.2 二维码只编码一个 URL 前缀

```
标签二维码内容 =  {BASE_URL}/{资产编码}
示例：           https://你的服务器/api/scan/EX-LAP-2026-0001
```

- `BASE_URL` 是部署时配置的**固定地址**（如 `http://内网服务器:8088/api/scan/`）。
- 二维码**只存编码**，不存任何易变信息。设备变更后无需重打标签，只需更新数据库。
- 物理标签与数据库通过"编码"这一唯一键解耦：标签是身份证，数据库是档案。

### 2.3 物理唯一性的边界

一旦打印并贴附：
1. 编码、SN、品牌、型号等稳定字段**锁定**；
2. 若必须更正（如 SN 录入笔误），视为"该标签作废 + 重打"，不可原地涂改；
3. 标签尺寸建议 50×30mm，内容极简（品牌 / 编码 / 名称 / 配置·SN / 二维码）。

## 3. Event Sourcing 式审计留痕设计

### 3.1 核心思想

不用"更新即覆盖"，而用"**只追加事件**"。每一次资产状态变化都作为一条**不可变事件**写入审计日志：

```
assets          —— 资产当前状态表（最新快照）
operation_log   —— 审计事件表（全量历史，只追加）
```

`operation_log` 关键字段：

| 字段 | 说明 |
|---|---|
| `event_id` | 事件唯一 ID（UUID） |
| `asset_code` | 关联资产编码 |
| `event_type` | 入库 / 领用 / 退库 / 调拨 / 维修 / 盘点 / 变更 |
| `operator` | 操作人（自由文本，需规范取值） |
| `from_state` / `to_state` | 状态前 / 后 |
| `timestamp` | 操作时点（UTC + 本地） |
| `note` | 备注（交接单号、审批单号等） |

### 3.2 为什么不用"更新覆盖"

- 覆盖式更新会**丢失"谁在何时改了什么"**，事后无法回溯；
- 审计的本质是**重建任意历史时点的状态**，Event Sourcing 天然支持；
- 即使当前快照被误改，也能从事件流重算还原。

### 3.3 operator 字段的规范

- 自由文本极易写成"我""管理员""system"等无意义取值；
- 应建立**规范取值白名单**（如 `数据校准` / `系统自动` / `资产管理员(代XX)`），并在录入时强制选择，避免审计时无法归责。

## 4. 盘点机制

### 4.1 盘点节奏

| 类型 | 频率 | 范围 |
|---|---|---|
| 日常抽盘 | 每月 | 高价值 / 高频流动设备 |
| 全面盘点 | 每半年 | 全量资产 |
| 离任盘点 | 每次 | 离职 / 调岗人员名下资产 |

### 4.2 盘点流程（闭环）

1. **导出基准**：从 `assets` 导出当前在用清单（含编码、使用人、位置）。
2. **现场扫码**：逐台扫码，系统标记"已盘到"。
3. **差异识别**：
   - 盘盈（实物有、账上无）；
   - 盘亏（账上有、实物无）；
   - 状态不符（账上在用、实物闲置）。
4. **差异报告**：生成 `差异清单`，每条附责任人 + 说明 + 处置建议。
5. **事件留痕**：差异核对结果作为 `operation_log` 的 `盘点` 事件写入。

### 4.3 准确率口径

- 不建议承诺"账实相符 100%"作为**起点指标**——它依赖系统权限、历史数据质量等前置条件。
- 更稳妥的口径：先达到"手工台账可达的阶段性水平（如 99%）"，待系统权限到位、历史数据校准完成后，再上调目标。

## 5. 责任交割与生效时点设计

### 5.1 为什么需要"生效时点"

人员离职 / 调岗时，资产责任必须从 A 转移到 B（或回收到库）。模糊的交接 = 事后扯皮、账实不符无人背。

### 5.2 交割四要素

| 要素 | 内容 |
|---|---|
| 标的 | 具体资产编码清单（非口头"电脑一台"） |
| 时点 | 精确到日的移交完成时间 |
| 双方确认 | 交出方 + 接收方（或资产管理员）双签 |
| 事件留痕 | `operation_log` 写入 `退库`/`调拨` 事件，operator 明确 |

### 5.3 生效前提（防"交割真空"）

- 交割单**双方签字 + 系统事件写入**后才算生效；
- 生效前资产仍由原责任人承担；
- 生效前的"未完结事项"（在修、待报废、待核销）需单独列出，不随交割自动消失。

## 6. COBIT · ITIL 的落地映射

| 框架要求 | 本方法落地动作 |
|---|---|
| COBIT APO13（安全管理）/ APO17（资产管理） | 资产分类、编码、责任人绑定、权限分级 |
| ITIL 资产管理与配置管理 | `assets` 作为配置项（CI），状态机驱动 |
| ITIL 变更管理 | 每一次状态变化 = 一次受控变更事件 |
| ITIL 事件 / 问题管理 | 盘亏、故障、异常作为事件登记并归因 |
| ISO/IEC 19770-1 | 资产标识、生命周期阶段、可审计记录 |

---

## 7. 数据安全与脱敏原则（发布红线）

- 资产系统**绝不**把真实企业名、员工姓名、PII、资产编码、内网地址推送到任何外部 / 公网仓库；
- 对外分享的只能是**方法、代码、脱敏后的结构**，不能是数据与真人；
- 发布前必须对**工作区与 git 全历史**双重复核：公司名 / 人名 / 业务编码 / 内网地址 / 真实数据文件 / 凭据 / 本机路径；
- 一旦敏感内容进过 commit，删文件不够（历史仍在），需重写历史后强推。

## 8. 一页纸 checkpoint

- [ ] 编码规则固化且永不改已生成编码
- [ ] 标签只含稳定字段，二维码只存编码
- [ ] `operation_log` 全量追加、operator 规范取值
- [ ] 盘点差异有报告、有责任人、有事件留痕
- [ ] 责任交割四要素齐全且系统生效
- [ ] 对外发布前工作区 + 历史双检零泄露
